# Riff Radar Project Diary

Plain-language updates for people following the project, written at the end of a working session. Newest entries first. Keep these readable by anyone — no jargon, no code; the technical record lives in decisions.md and git history.

## 11 September 2026 — Setting up the ground rules for coding assistants

The goal today was housekeeping rather than building: give the coding assistants a clear, written answer to three questions they kept having to guess at. Where do tasks and specs live? What words do we use to mark a task as "ready" or "needs more detail"? And which documents should be read before touching anything? Those answers now live in a new `docs/agents/` folder, with a short summary in `AGENTS.md` pointing at them. Tasks will be kept as plain markdown files in the project rather than in an external tool, which suits a small solo project and keeps everything in one place.

Two things came out of it that were worth catching. The project brief had moved into the `docs` folder at some point, but several documents still pointed at its old location — those are fixed. And the assistants' default setup expects one file per decision in a `docs/adr/` folder, which contradicts our existing habit of keeping all decisions in a single `decisions.md`. We kept our habit and wrote the difference down, so nobody quietly starts a second decision log. Next: back to the actual product work, starting with the first milestone in the project brief.

## 11 September 2026 (later) — Pinning down what the first working version actually does

The goal was to define Milestone 1 and nothing else: no code, no later milestones. We worked through it as a long question-and-answer session, starting from how Ben actually finds new music on a Friday morning and working outward to what the software should do. That starting point turned out to matter, because the real habit differs from the original plan in ways worth knowing about. The plan assumed the system would search the web; in practice Ben reads four specific websites he trusts. The plan assumed it would look at albums that had just come out; one of those sites lists albums that haven't been released yet. Both differences are now settled in favour of the real habit, which means the project brief needs a small edit that hasn't been made yet.

The session produced three documents: a glossary of the project's own words, twelve recorded decisions with the reasoning behind each, and a specification of the first milestone covering the command, the sources, what counts as an eligible album, how taste is described, what the agent is allowed to do, when it stops, what gets recorded, and what stops it writing to Notion. Two useful things surfaced along the way. Ben's own mental model of taste is simpler than the one proposed — lock in the favourites, block the ones he won't listen to, and let everything in between be surfaced by looking at labels, band members and genre — so the design was simplified to match. And the existing Notion database is missing five fields the first version needs, so those have to be added by hand before anything can run. Next: agree the brief edits, add the Notion fields, then start on the loop itself.

## 11 September 2026 (later still) — Choosing the tools and deciding where to test

With the first milestone defined, this session settled two things that had been left open: what to build it with, and where the tests should attach. The language is TypeScript, chosen on the grounds that Ben already thinks in it — working in something less familiar would spend effort on the language rather than on the agent loop, which is the whole point. The thinking model will be DeepSeek V4.1 Flash, rented from a hosting company called Fireworks rather than run locally. Almost nothing extra is being installed: recent versions of Node can already run tests, talk to the internet and store data in a database file, so the project takes only three small libraries.

The more interesting decision was where to put the test boundary. Everything unpredictable or outside the program — the model, the internet, the clock — goes through a single doorway that tests can substitute. The database deliberately does not, because a fake database would make the save-and-resume tests prove nothing. A gap also surfaced: the chosen model does not guarantee its answers match the expected shape, and the spec never said what happens when the agent proposes something malformed. It now retries up to three times and then stops. Two loose ends remain: the model's exact name and price could not be read from the outside, so Ben needs to copy them from his Fireworks account. Next: run /to-spec to turn this into an implementable specification.

## 11 September 2026 (end of day) — Borrowing a shape from the team's framework

A short follow-up settled how the project's files will be arranged. Colleagues of Ben's use a framework called Flue for this kind of work, and the plan is to build this one by hand first and possibly move to the framework later. So rather than inventing a structure, the project copies Flue's arrangement wherever that makes sense and ignores it where it doesn't — Flue expects an agent to be reachable over the web, and this one is a command you type, so the entry point differs by design. The payoff is that the cost of moving later is now visible up front: the two files a framework would take over are clearly separated from the rules and the data-fetching code, which would carry across untouched. Pleasingly, the file that would be thrown away is exactly the one the whole exercise exists to teach.

One small deliberate difference was recorded so nobody later mistakes it for an oversight: the framework uses one data-checking library and this project uses a different one, simply because Ben already knows it. Also confirmed the model's real name and prices, which turned up something worth catching — repeated text is charged about thirty times less than new text, so the record now counts the two separately, otherwise the running-cost figures would have been badly wrong. Next: turn all of this into an implementable specification.

## 14 September 2026 — The first code: a run that starts, stops and leaves a record

The goal was the first half of the first ticket, and deliberately only that half: make a run exist, without building the thinking part yet. So there is now a command you can type, a place for the settings, a database that records what happened, and a run that starts up, works out exactly which dates it is covering, writes down what it did, and stops — reporting honestly that it found nothing, because nothing has been built yet that looks. It sounds like very little, and that is the point: every safety rail the thinking part will need is already in place and already tested, so when it arrives it drops into something that already stops properly. Sixty-nine tests cover it, and a run can be read back out of the database with an ordinary database query and no special tools, which was one of the things we promised ourselves.

The interesting question of the session was what "the last seven days" actually means. A run started on a Friday morning in Sydney is, as far as the rest of the world's clocks are concerned, still Thursday night, so a naive reading would have quietly looked at the wrong week. It now uses local dates, counts today as one of the seven, and — importantly — writes the two real dates into the record rather than the number seven, so that reading a run back in six months still tells you what it covered. Two things need Ben's eye. A fourth small piece of tooling had to be installed to make the type checking work at all; it only exists while writing code and disappears at runtime, but it is one more than the three we said we would use, so it is written down as a decision awaiting approval rather than slipped in. And the run does read the taste file, slightly ahead of the ticket that formally introduces it, because the record it writes has to say which version of Ben's taste produced it. Next: the second half of the ticket — the loop itself, the part the project exists to learn.

A follow-up pass the same day cut the code back hard: 175 lines gone, no behaviour lost that anyone would miss. Most of it was machinery written out of habit rather than need — a credentials object carefully assembled and then thrown away unread, a hand-written date formatter that the language already ships, a hand-written error formatter that the validation library already ships, a directory-walker Node does in one call, and several small wrappers with exactly one caller each. Four things did change in ways worth knowing: the record now stores the command exactly as typed rather than a tidied-up version of it (the two real dates beside it carry the detail anyway), the taste-file error report is now the validation library's own wording, the shorthand for running the tool directly was dropped in favour of the one documented way, and the check on the date window now happens only where the command line is read instead of in two places that could drift apart. Six tests went with the code they covered. Next is still the loop.

## 14 September 2026 (later) — The loop itself

The goal was the second half of the first ticket: the part the project exists to teach. The agent now thinks. Each step it is asked what to do next, it answers with one action, and the program checks that answer before acting on it — and only then does anything happen. The four things it can ask for are fetching one of the three configured sites, looking a record up in MusicBrainz, searching the web, and finishing with its shortlist. Three of those still return made-up data on purpose, because the point of this sitting was the loop and its safety rails rather than the music; the real versions drop into the same slots over the next few tickets and nothing else has to change.

What matters is what happens when the model gets it wrong, which it will. An answer that is prose instead of an action, an answer that names a tool that does not exist, an answer whose details are malformed or simply the wrong shape, an answer proposing two actions where one was asked for — each is refused, written into the record as refused, and handed back to the model so it can correct itself. Three of those in a row and the run stops. So does thirty steps, or a quarter of a dollar spent, or a shortlist that does not meet the rules, or the model provider failing outright. Nine possible endings, exactly one recorded, and every one of them now has a test that drives it through a stand-in model. The record keeps what the model proposed, whether it was allowed, what was actually done, how long it took and what it cost, split into the three kinds of token because the cheap kind is thirty times cheaper and lumping them together would have made every future cost figure wrong.

Three things need Ben's eye. A quiet week — the model finding nothing worth proposing — is recorded as "nothing found" rather than as a failure, which is written down as a decision. The spending ceiling per run is set at 25 cents, also written down. And one promise in the ticket is still outstanding: we cannot yet confirm whether the model provider tells us how much of each request it served from its cache, because there is no API key in this sandbox. The machinery for both answers is built and tested, and a single command settles it — until then a run that gets no cache figures labels its own cost as a ceiling rather than a measurement. A short follow-up once the key arrived settled both outstanding questions, and turned up a third nobody had asked. The provider does report how much of each request it served from its cache, so running costs are a real measurement rather than a ceiling — and the numbers vindicate the design: after the first step, roughly nine tokens in ten are the cheap kind, which is the whole reason the unchanging part of the request was put at the front. The surprise was that the model, asked to choose one action, cheerfully asked for all three websites at once. Refusing that is correct and was already built, but a run would have refused the model's first perfectly sensible move three times and given up before fetching anything. The fix is to ask the provider to allow only one action at a time, which it honours; the refusal stays behind it as the guard, because a request is not a guarantee.

With that, the whole thing ran for real: nine steps, three site fetches, five record lookups and a shortlist of five, in about thirty-six seconds for a fifth of a cent. Every step is in the database with what was asked for, whether it was allowed, what came back, how long it took and what it cost, readable with an ordinary SQL query. The music is still invented — that is what the next tickets fix — but the loop, the rails and the record are real. Next: ticket 02, which replaces the first fake with real pages.

## 14 September 2026 (later still) — The music is real now

The goal was ticket 02, and only that: make the first of the three fake tools real. The agent now actually reads the three websites Ben reads. It asks for one, the page comes back, the markup is stripped out by hand — no library, because the model only needs the text to be legible, not perfect — and the text is handed to a second, much simpler model call whose only job is to turn a page of listings into a list of releases. That list comes back as data the program can count, tidy and compare, which is the part that matters: the same album listed on two of the three sites is now recognised as one record carrying both addresses, and where two sites disagree about the release date, both dates are kept and the disagreement is written down rather than quietly settled by whichever page was read first.

The decision worth knowing about is that second model call. It would have been possible to just hand the page text to the agent and let it hold the releases in its head, and that would have been less code — but then there would be nothing to deduplicate, nothing to count, and no way to notice a site that has stopped producing results. So the extraction is its own small call, and everything after it is ordinary arithmetic that can be tested without a network. The cost of that call is charged to the step that made it, otherwise the spending ceiling would stop working at exactly the moment the tokens get big; and the page text is capped before it is sent, because a full release calendar costs more than a whole run is allowed to spend. The page itself is stored whole in the database, so a bad reading can be examined later without going back to the website — which may by then have changed.

Three things need Ben's eye. A site that refuses us, lists nothing, or comes back unreadable no longer stops the run: it is recorded as a warning and the agent carries on with the other two, on the grounds that losing one of three sources is a degraded week and not a failed one — written down as a decision. The second model call is likewise written down as a decision, since the ticket left it open. And the test fixtures are hand-written rather than recorded from the real pages, because this sandbox has no outbound network access; they reproduce each site's shape faithfully enough to test the stripper and the client, but only `npm run smoke:sources` — run by hand, with a key — can confirm the real pages still look like that. That is the first thing to run when a key and a network are both available. Next: ticket 03, web search.

A follow-up once the network was opened up replaced two of the three hand-written test pages with the real thing, and the real thing corrected us twice. The Loudwire calendar lists the coming months first and the weeks just gone at the very end, so the cap on how much of a page we send was cutting off exactly the releases a backward-looking run asks about; and a calendar covers a year, so one fetch would have handed the agent a thousand releases and paid to resend them at every step afterwards. Discovery is now asked for one week at a time and the cap is sized from a real page rather than guessed. Both fixes came from looking at a page we had previously only imagined, which is the argument for keeping the captures whole and untidied.

Live, the two readable sources between them found twenty-six albums released in the past week, for a little over a cent. The third — Album of the Year — turns out to refuse us at the door: it answers every request with a bot challenge, and getting past that would mean pretending to be a browser on a site that has explicitly said no, which is not something this project should do. Ben's call was to run on the two that work, so the third is no longer configured at all rather than configured and failing — a run has thirty steps and spending one knocking on a shut door buys nothing but a warning we already know the wording of. The page it served is kept as evidence, and its address sits in the decision record one line away from coming back if it ever opens up or someone finds a replacement. Worth knowing too that reading the Wikipedia page took a minute and a half of model time — discovery is the slow part of a run now, and the whole thing still costs less than two cents. Next: ticket 03, web search.

Ben ran the whole thing for real at the end of the day, and it worked: ten steps, two live websites, a shortlist of five albums actually released in the past week, for under two cents. Three of the five were found on both sites and correctly recognised as the same record rather than counted twice, which is the thing the dedup was written for and the first time it has been seen doing its job outside a test. The cost breakdown was the pleasing part — reading the two pages accounted for almost all of it, and every step after that was billed at the cheap rate, so the loop itself is nearly free and it is discovery that costs money. Worth writing down, because it means the lever for making runs cheaper is the pages, not the thinking.

One thing is important not to mistake for success. The albums, the dates and the web addresses are all real, but the identity check is still the stand-in from the last ticket, so every MusicBrainz identifier in that shortlist is made up and the agent's one-line justifications say "confirmed" about a confirmation that was fabricated for it. The agent is reporting honestly what it was told; the tool lied. That is exactly what the next ticket replaces, and nothing writes to Notion until two tickets after that, so no invented identifier can escape — but it is the sort of thing that looks finished and is not, so it is written down rather than admired. Next: ticket 03, web search.


## 14 September 2026 — ticket 03: the second fake becomes real

The goal was ticket 03 and only that: make `web_search` a real search. Brave's API was Ben's pick over scraping DuckDuckGo — which blocks anything that does not claim to be a browser, and this project does not claim that — and over Wikipedia's search, which is too thin for underground metal. It answers with JSON over a plain GET and takes its key in a header, so the only change the seam needed was an optional headers argument on `http`, added to what the project already sends rather than replacing it. A search that is refused, rate-limited, empty, or answers with something unparseable is a warning on the step and the run keeps going, exactly as a disappointing source already did.

The more interesting half was not the search. The rule that a release may only come from one of the configured sites has lived in the prompt since the beginning, which means it has been a request rather than a rule: nothing stopped the model shortlisting something it read in a search result, or simply remembered. The shortlist validator now takes the run's discovered releases and rejects any item that names something else, and since only a source fetch can add to that list, the route from a search to a Notion row no longer exists in the code. Proving it meant breaking seven existing tests whose shortlists were invented, which is the useful kind of test failure: they had been asserting on releases no source in the test had ever listed. What remains is Ben's: `npm run smoke:search` with a Brave key, to check that the body Brave really serves is the shape the client parses — the automated test uses the documented shape, not a capture, because capturing one needs the key. Next: ticket 04, MusicBrainz, the last fake.

## 15 September 2026 — ticket 03 closes: Tavily, a POST, and a real capture

The goal was to finish ticket 03, which had been sitting at `ready-for-human` waiting for the one thing the repository did not have: a key, and therefore a live search. Ben supplied one — for Tavily, not Brave — so the provider changed before Brave was ever used. That turned out to cost almost nothing, which is the useful thing this session proved about the seam: the endpoint, the credential name and the response schema moved, and the client either side of them did not. Tavily wants its query in a JSON body, so `http` gained a `post` beside its `get` rather than being generalised into a `request(method, ...)` — only one caller posts, every source is and will remain a GET, and the general version would have rewritten every existing caller to buy nothing. The visible cost was in the test fakes: every inline `{ get }` now has to say what it expects, and each refuses the other verb. That is noise, and it is the honest kind, because it says out loud that a source is a page and a search is not.

The better outcome is that the search client no longer runs against a body nobody served. `fixtures/tavily-search.json` is a real response, captured before a line of the client changed, and the client was then written to parse it — which meant `npm run smoke:search` passing afterwards was confirmation rather than discovery. ADR-0032 had said the first real response should replace the invented one; it did, and the discomfort that decision recorded is gone. One thing Ben asked for was not done and should not be quietly forgotten: `tavily.com/agent-setup/SKILL.md` could not be read, because the path redirects to `www.tavily.com` and the sandbox denies that host. The live API's actual behaviour was the source instead, which is stronger for the search call itself but says nothing about any setup step that document might prescribe. Next: ticket 04, MusicBrainz, the last fake.

Afterwards Ben allowed `www.tavily.com` and the setup document finally opened. It was worth reading, though not for the reason expected: almost everything it asks of an application integration was already true, and the one thing it caught was small and real — Tavily documents a 400-character ceiling on a query and the action schema had no upper bound, so a model writing a paragraph into `web_search` would have spent a step learning that from the provider. That is exactly the class of thing AGENTS.md means by validating a model-produced action before dispatch, and it was missed because the live API answers a long query rather than refusing it. The document also has a setup path that installs the `tvly` CLI and Tavily's Agent Skills globally into the coding agent; that equips the machine rather than this repository, so it was left for Ben to decide rather than run quietly.

## 15 September 2026 — ticket 04: the last fake, and what the live service taught

The goal was ticket 04 and only that: make `lookup_release` real, and turn the brief's eligibility rules into code. Three decisions were Ben's before a line was written — eligibility enforced as a guardrail at `finish` rather than by filtering candidates, a release nobody looked up counted as missing data and excluded, and the EP track threshold paid for with a second request made only for an EP — and having them settled up front is what kept a fifteen-criterion ticket to four coherent commits.

The lesson of the session was how much the live service taught that no fixture would have. Four things, each of which changed the client: MusicBrainz answers HTTP 200 with an error in the body when it is busy, so a 2xx is not by itself a result; it sheds load often enough that giving up on the first refusal would leave candidates unverified for no better reason than the hour of the day; its search is fuzzy and scored, so asked about Ulcerate it cheerfully offers an EP by Ulcerate Fester, a different band; and it serves partial dates like `1985`, which a first draft treated as undecidable and would therefore have excluded a forty-year-old reissue as a mystery rather than as a reissue. The smoke test earned its keep on the first run by failing, and the near-miss between those two bands is now the EP case in it, so the match rule is exercised rather than assumed.

The happier discovery was that two of the brief's rules needed almost no code, because MusicBrainz already draws the line: a reissue and a remaster live *inside* the original's release group, so they exclude themselves on its date, while a total re-record gets its own group and qualifies like any other new album. Exodus proved both — one group dated 1985 holding fifteen releases, and a separate group for the 2008 re-record. One rule the data cannot support is written down rather than faked: a covers album is its own release group and MusicBrainz has no type for one, so nothing excludes it, and ADR-0034 says so. Nine agent tests broke, all of them proposing shortlists no run could now produce, and one of those failures was a real bug — the rate limiter assumed a monotonic clock and would have stalled for a day when a test restarted one. Next: ticket 05, the taste profile and ranking.

Two review passes afterwards were worth more than the implementation in one respect: they caught a claim rather than a bug. The gap section said "another band's version is excluded by the match rule", which is wrong — the match rule stops a candidate binding to the *original* band's release group, but a source listing a cover band's own album matches that band's own release group and sails through. Three of the four re-record sub-rules are unimplemented, not one, and label and personnel are not fetched at all. All of it is written down now, because a ticket that marks itself done while overstating what it did is worse than one that leaves a box unticked. The other useful finding was self-inflicted: the client's tests spent thirteen seconds asleep, having carefully extracted the rate limit's arithmetic into a pure function so it could be proved without waiting, and then sleeping through the backoff anyway. The backoff now owes the gate more time rather than sleeping again, so there is one sleep in the file and the clock drives it; that file's tests run in a third of a second. Ben then accepted the re-record gap as scope rather than debt: a covers album, a partial re-record and another band's version all pass, and the records are rare enough that the slots they would cost are not worth a rule MusicBrainz's data cannot support. That is written into ADR-0034 as a closed decision so ticket 05 does not inherit a phantom obligation — the label and personnel deferral and the split proxy are not covered by it and stay open. He then overturned the split proxy, which was the better outcome of the two: excluding every two-artist release to catch splits was answering the wrong question, because a split and a collaboration are identical in MusicBrainz's data and the thing actually being asked is whether Ben wants to hear it. The lookup carries the credited artists' names now instead of their number, and one excluded artist sinks a release however many others are on it. That incidentally enforces a rule the prompt has claimed since the first version and no code ever applied — the same shape as the provenance rule in ticket 03 — so the `artists.always` half stays with ticket 05, where ranking lives, and a live album does not become eligible because a favourite plays on it.

## 15 September 2026 — ticket 05: the profile finally does something

The goal was ticket 05 and only that: make the taste profile change what a run proposes, and stop a re-run proposing what Notion already holds. Four decisions were settled before any code was written, which is the second time that has been worth more than the implementation. The one that shaped everything else is who decides the order of the shortlist. The answer is the code: the model chooses which releases are worth proposing and writes the reasons, and then arithmetic scores each one against the profile — artist tier, label, genre, personnel — and rewrites the ranks from the result. Where the profile has nothing to say about two records, the model's own preference survives as the tie-break. The upshot is that "the profile changed the order" is provable without a model at all: the same scripted output under two different profiles produces two different orders, and the finish step writes down every contribution beside the profile term that caused it, so an ordering can be recomputed by hand from the trace.

The other three decisions each removed a way of being wrong. An artist on the `always` list is a guaranteed slot rather than a large number, so no combination of weights can outbid it and nothing has to be tuned to make sure of that — and leaving an eligible one off the shortlist now refuses the shortlist, which is a promise the prompt has made since the first version and no code had ever kept. A vibe note is the one judgement of the model's that scores, and only where its quote is found verbatim in a page the run actually stored; an invented quote is not a failed run, it simply counts for nothing, because a Friday's shortlist should not be spent on a transcription slip. And Adjacency stopped being a word: label, genre and band members are three separate resources at MusicBrainz, so a lookup now costs four requests and about thirteen seconds instead of one. That is time rather than money, and the alternative was ranking three of four signals on data the run never asked for.

Two useful things came from the live service rather than from thinking. `[no label]` is a real entry in MusicBrainz meaning a self-released record, and reading it as a label would have made it matchable by a profile term — the smoke test served it on the first run. And the ticket's open question about genre coverage in the long tail is now answered: Ulcerate returned six tags and a 1991 EP by a different band returned none, so genre is weighted no higher than label. The review then caught a real bug that neither had: artist tiers were matched by containment, so `Ulcerate` on the always list would have guaranteed a slot to Ulcerate Fester — the very near-miss the match rule was built to catch one ticket earlier. Names are matched whole now; labels and genres still match inside a longer value, which is what makes "death metal" find "dissonant death metal".

Two things are waiting on Ben and neither is code. Notion has never been reached: `api.notion.com` is denied to this sandbox, so the suppression client is written against the documented shape with its test bodies declared inline — which is the right call anyway for a database holding his listening queue — and `npm run smoke:notion` is what will turn it from plausible into confirmed. And `taste-profile.json` is still all empty lists, which means every release currently scores zero and the ranking changes nothing. Every mechanism that reads it is built and tested; the file is hand-edited by definition. Next: fill the profile, run the Notion smoke test, then ticket 06, the Notion write.

Late addition, the same day: Notion was opened up and a key supplied, and the smoke test justified itself on its first run. It read zero identities out of 272 records, because the database's title column is called `Album` and the specification had said `Title`. Every automated test had passed — against bodies this project wrote itself, all of which agreed with the code about a name that was wrong. Only the real database disagreed, which is the whole argument for keeping one live test per integration. Ben's call was that the database wins over the document: it predates the spec, holds hundreds of hand-entered records, and is the thing he actually uses. Suppression now reads 272 identities in a second and a half, and none of them carries a MusicBrainz identifier, because a person typed them in — so it rests on artist and title until the agent starts writing rows itself, which is exactly why the read returns both forms of identity. Two more differences are written down for ticket 06 rather than fixed here: the Apple Music column is spelled without "Link", and there is no album-cover column at all yet.

## 16 September 2026 — ticket 06: the shortlist reaches Notion

The goal was ticket 06 and only that: a completed run puts its shortlist in Ben's database, once, with `Status = Proposed` and a link he can tap. Two decisions were settled before any code was written, and both turned out to be about *when* rather than *what*. The schema preflight runs at the start of a run rather than in front of the write, because the answer is identical either way and finding out first costs no model tokens, no run row and no half-minute of MusicBrainz lookups — a database missing a property refuses the run and names what is missing, and the agent never adds it. And a write that fails part way through archives the rows it already made, because Notion has no transaction and the quieter alternative is worse: the three rows that landed would suppress themselves next Friday, so the two that did not would never be proposed again. That rollback is the reason the `http` port gained a `patch`, the third verb for the third caller that needs one.

The thing worth keeping is how `Rating` is protected. The ticket asks that the agent never write it by any path, and the way to mean that is not a check — it is that one table in `config.ts` names every property, both the preflight and the page builder read it, and `Rating` is not in it. There is nothing to bypass. The same table is why the preflight and the write cannot drift apart. Live, the preflight passed on its first run: every one of the five properties the specification marked as new already exists in Ben's database with the right type, so `npm run smoke:notion` now confirms the schema and prints the page a real item would become without posting anything.

Two things are Ben's. `coverartarchive.org` is denied to this sandbox, so the cover fetch is tested and has never met the archive — `npm run smoke:coverart` fails closed rather than passing on an unreachable network, which is the shape that lesson took last time. And nothing has actually been written to Notion yet: every automated test and the dry run agree with each other about a body this project wrote itself, which is exactly the agreement ADR-0041 caught being wrong. One real run without `--dry-run` settles it. Next: ticket 07, the milestone evidence run.

Later the same day, a real run stopped at `tool_failure` three steps in, and the trace answered the question it exists to answer: two sources read, then a MusicBrainz lookup that died saying `fetch failed` and nothing else. Two faults behind one symptom. The message was useless because `fetch` hides the cause — the `ENOTFOUND`, the reset, the timeout — in a property nobody read; and the classification was backwards, because every client treated an answered refusal as a warning and let an unanswered request throw past it and end the run. The adapter now returns a dead socket as status zero with the reason in the body, which every client's existing "did this answer?" branch already knows how to handle, so a source degrades, a search degrades, and a lookup retries three times before settling for Unverified. The `http` port promises never to reject at all now, which is a stronger contract than ADR-0018 wrote and a much simpler one to keep. Next: re-run, then ticket 07.

## 16 September 2026 (later) — the first real write, and the guardrail the model could not see

The outcome this session was not a ticket but a whole-repo audit for over-engineering, and then acting on it. The four that died died for the same reason: a read-only scan can see that something *looks* redundant but not what it is holding up. `categorised()` reads like a wrapper that only delegates, but inlining it at its three call sites is longer than leaving it. `defineTool` reads like an identity function, and it is, but deleting it widens every tool's `run(input)` to `unknown`, because TypeScript cannot infer per-key generics in an object literal without a helper — `satisfies` does not substitute. `coverart.ts` reads like six lines that should live in `notion.ts`, but the Cover Art Archive is its own live integration and AGENTS.md asks each of those for its own smoke test. `store.runOf` reads like a prefix scan where an exact query belongs, and the prefix scan is already the lazy option because it reuses the row mapping. The first of the two held back is `assertSchemaIsCurrent`: replacing thirty lines of column diffing with a `user_version` stamp is a genuine simplification, but the only way to do it without either a migration or a false alarm is to declare the current schema version zero, which silently gives up the check for exactly the databases it was written for — including the 11MB one holding six milestone traces. It stays.

What did land: the bespoke layering linter is gone (ADR-0056), `parseCliArgs` now tokenises with `node:util`'s `parseArgs` (ADR-0057), the `Store` interface is `ReturnType<typeof openStore>` since ADR-0018 already says the database is real in tests and never substituted, `finishRun` and `abortRun` share the UPDATE and the one-reason-per-run guarantee they had been spelling out twice, and `httpAdapter`'s three methods are three ways of calling one `request`. Net −177 lines and 472 tests green, against an audit that claimed −400: the gap is the five that were dropped, and the estimate was made without reading the call sites. One behaviour changed, `--last-days=14` is now accepted, and its test was rewritten rather than removed. Ben settled both held items on the spot: the schema check stays as it is, and `exactOptionalPropertyTypes` stays on, because types should be strict — an absent property and an undefined one are genuinely different things here and the spreads are the price of saying so. Both are closed rather than deferred. Next: milestone 3.

## 18 September 2026 — defining milestone 3, and nothing else

The outcome was a definition: `.scratch/milestone-3-measurable-system/spec.md`, a carried-forward file, eight tickets, ADR-0058 to ADR-0065, six glossary terms. No code changed. The session was a grilling, and the useful part of it was that three of my recommendations were wrong and the corrections came from Ben knowing things about his own data that no amount of reading the repository would have surfaced.

Two facts decided most of the shape and both were measured rather than assumed. The first: both Sources are *year* pages, and the URL never varies with the window — `sources.ts` fetches the whole 2026 calendar every run and filters twice. So `fixtures/loudwire.html`, captured on 14 September, carries all twelve months, and a January window is replayable against bytes already committed. Historical back-testing needs no network and no new capture, which is the difference between an idea and a ticket. The second fact came out of checking whether truncation would spoil it: Loudwire cleans to 47,083 characters against the 80,000 cap and is not truncated at all, but `fixtures/wikipedia.html` cleans to 124,831 and loses 36% of itself — and the loss is chronological, so it falls on the *later* months, which is precisely what a backward-looking run queries. A real run asking for last week reads a Wikipedia page with roughly half of that week's entries cut out. The system already warns (ADR-0030); what was unknown was the magnitude and the bias. It is carried-forward item 1 rather than a ticket, because it is source-coverage work and this milestone is about measurement — but it is why the Defect vocabulary has a seventh word, `unlisted`, for a release no Source carried. Without it a truncation bug is counted as the model being bad at its job and fixed in the wrong half of the system.

The corrections are worth recording because each was a real design fault. I proposed reading Ben's Notion ratings back and did not notice that ADR-0042 says in terms that no code can name `Rating` — the guarantee being that the agent cannot overwrite his verdicts. The collision is real and the resolution is an amendment rather than a workaround: no *write* path may name it, which is weaker as a sentence and identical in effect. Second, I proposed excluding back-test weeks holding more than five known albums, so that the five-item cap would not distort recall; Ben pointed out that the cap exists *because* weeks with thirty releases were common, so excluding busy weeks selects exactly the quiet ones and biases the sample toward easy cases. `hits / min(k, 5)` reads as recall below the cap and as precision-against-known above it, excludes nothing, and is one line. Third, he asked whether he should clean up the Notion record — remove what he now thinks should not have made the cut. Deleting would have been a live behaviour change dressed as housekeeping: `suppressedReleases` reads the whole database unfiltered, deliberately, so every deleted row becomes proposable again. Curating by `Rating` costs nothing, keeps suppression intact, and feeds the taste metric he wanted in the first place.

A fourth correction came after the tickets were written, and it is the same mistake as the second. I defined the Known Set as the rows rated `Rotate` or `AOTY`, reasoning that those are what a five-item run should have found. Ben's answer was that most weeks hold only a handful of rated albums, so that restriction would discard most of the reference set to solve a problem that only arises when a week is busy — and that `OK` should count, because it means he listened and it was fine, which is a release the agent was right to surface. The rule is now that `Nope` is the only exclusion, which is exactly what ADR-0063 already said curation *meant* before I added a second bar on top of it. `Rotate`/`AOTY` survives as a secondary number reported only where `k > 5`: when the cap forced a choice, did it choose well. Rows left unrated are excluded and counted, since an unrated row cannot be told apart from a `Nope`. ADR-0063 was corrected in place rather than superseded — it was accepted the same day and no code had been written against it.

What I am least sure of is the Known Set's size. Eight months of hand-entered rows sounds like plenty until it is bucketed by week and stripped of anything the agent itself wrote or Ben never got round to rating; if too much of it stays unrated, the back-test is a number with an n too small to read, and the honest response is to publish the n rather than loosen the rule that produced it. The other thing worth watching is the ordering trap: ticket 01 was already written and is the milestone's controlled change, so it is now blocked by ticket 08 and must not ship before the baseline. It is a four-line fix and it will be tempting to make in passing — which is exactly why it is written down in three places. Next: ticket 02, the Defect graders, which everything else depends on.

## 18 September 2026 (later) — ticket 02: seven words for a wrong run

The outcome was `src/domain/eval.ts` and nothing else: the seven-value Defect union and one pure function per member, with `gradeRun` composing them and applying the one ordering rule the ticket sets — `unlisted` runs first and takes its releases off what `missed` is allowed to see. No migration, no new column, no change to `src/store/`, which is the whole point of ADR-0059: a Defect is a property of a grading, so a run cannot mark its own homework. The graders take an explicit `GradedRun` rather than a `Store`, so a test hand-writes a three-item shortlist and a two-step trace instead of needing a realistic 11MB trace nobody can read. Three of the seven are thin wrappers over rules that already existed and are called rather than restated: `ungrounded` asks `citedVibes`, `escaped` asks `isRetryable`, `misranked` asks `rankShortlist` for the order the run should have produced.

Two mistakes were caught by review and both were the same kind — a rule that passed its tests while being unable to fire on real data. `unlisted` searched the whole cleaned page for the artist and the title, which is a rule that cannot work: on a 120,000-character calendar almost any artist substring and almost any title substring co-occur somewhere, so a genuinely missing release would have been reported as listed. It now matches both halves on the *same line*, which is a fact about these pages rather than a nicety — `htmlToText` keeps a calendar row on one line by design (ADR-0013) — and the lines are split before normalising, because `normaliseName` collapses the newlines it depends on. `escaped` emitted one finding per retryable step in any `tool_failure` run, so three transient retries the run *survived* plus one terminal refusal read as four escapes. It now identifies the fatal failure by position, the same rule the repair counter follows (ADR-0053), and counts once per run. Both fixes bought tests: the same-row case, and a run that recovered from a transient before a refusal killed it.

Three smaller things. `wasteful` was gating on `WRITE_PERMITTED`, which holds the same two termination reasons for an entirely unrelated reason — what may reach Notion — so it has its own list now and will not move when the write policy does. The `unlisted`-suppresses-`missed` composition keyed on the string `unlisted` happened to report; it keys on the normalised identity instead. That last one is worth flagging as unproven: the behaviour is identical today, so the mutant survived and no test pins it — it removes a coupling rather than fixing a bug. Nine other mutants of the load-bearing rules were killed. What review also established and I am recording so it is not re-litigated: `misranked` grades `3e657aa3` clean, and that is correct — when every score is zero no order contradicts the arithmetic, and a profile that should have scored and did not is ticket 01's bug, visible as `missed`. 501 tests, `npm run check` green. Next: ticket 03, the eval runner and case format, which is where `CaseLabels` and `CaseBudget` get their manifest schema.

## 18 September 2026 (afternoon) — ticket 03: a pass that runs

The outcome was the case format and `scripts/eval.ts`, and the proof is a live pass: `npm run eval --case 00-smoke` fetched the committed January calendar, asked the real model for thirty steps, graded the result and wrote a report. The runner is wiring and nothing else — the manifest schema, the seven graders and the pass arithmetic are pure and live in `src/domain/eval.ts` where the suite can reach them, which is the split ADR-0064 asked for. `git diff src/agents/ src/tools.ts` is empty, so the loop still does not know it is being evaluated.

Two design choices are worth recording because they were not in the plan. The first is that `responses` keys are URL *prefixes* and the longest match wins, which means a fallback needs no separate concept: `00-smoke` answers every MusicBrainz release-group query with one not-found body, and a harvested case will override it per release with a longer key carrying the encoded query. The second is what happens to a URL nobody recorded — it throws, rather than quietly 404ing, because a graded Defect has to be about the agent and not about a recording nobody made. The one deliberate exception is a configured source the case omits: that answers 404 and the run degrades with a warning, the way it would against a source that was down (ADR-0030). Both `sources` and `responses` resolve against `fixtures/` rather than against the case directory, so a body two cases share is referenced twice instead of copied twice, which is ADR-0062's rule applied to more than the two big pages.

The live runs are the interesting part, and there were two of the same case. The first ended `max_steps_exceeded` — thirty steps, 375 seconds, $0.0228 — and the second, after the review fixes, ended `no_candidates` in twenty-five steps, 165 seconds and $0.0120. Identical bytes, identical window, identical prompt: the model is the only thing that moved, and it moved the termination reason, the step count and the cost by roughly a factor of two. That is the noise floor arriving uninvited before the ticket that measures it, and it is worth saying plainly that a single-sample delta on any of those numbers would be unreadable. Neither outcome is a bug in the runner. With no MusicBrainz coverage at all every lookup comes back not-found, so the model spends its budget confirming that nothing can be verified; `wasteful` correctly stayed quiet both times, because the run never completed and the budget it blew past is the Termination Reason's business. Timing, not money, is the constraint nobody had estimated: a twenty-case pass is one to two hours of wall clock at $0.26.

Both reviews were worth their cost and one finding was a money bug. A URL nobody recorded threw, and the throw propagated out of the loop over the cases — so a missing recording on case nineteen would have discarded the report for the eighteen already paid for at the model. A case that throws is now reported and skipped, and the report is written regardless. Three more were real: the case format could not record a non-200 response at all, which meant no case could ever exercise `escaped` or `retry-after` — a format flaw worth fixing before twenty manifests exist rather than after, so a recording is now either a path, meaning 200, or an object carrying a status and headers. The report pinned nothing about what produced it, so two passes could not be told apart by prompt version, profile version or model, which is precisely what ADR-0058's comparison rests on. And `00-smoke` would have been counted as a twenty-first case, skewing the mean cost and median latency the readiness budgets are set against; a slug starting `00-` is now a fixture of the runner and skipped unless named. Smaller: a duplicated `musicbrainz-not-found.json` that the ticket's own criterion forbids, a test using a Notion schema as though it were a calendar page, and a missing fixture failing with a bare ENOENT rather than naming the case. `sample-report.json` stayed constructed rather than recorded and the README now says so outright — its four cases exist to exercise the arithmetic, and the real single-case pass sits beside it in `docs/evidence/eval-00-smoke.json`. 525 tests, `npm run check` green and still offline. Next: ticket 04, which is Ben's — curating and freezing the Known Set.

## 18 September 2026 (evening) — ticket 04: the half of a human ticket that was arithmetic

The outcome was ticket 04, which said "what to build: nothing" and was right about the part that mattered. Ben rated the rows himself; what he asked for was criteria 3 to 5 — the agent-written rows identified, the weeks bucketed with their `k`, and the unrated counted — and those are arithmetic over 288 rows rather than judgement about any of them. So there is a script after all: `npm run known-set`, read-only, with its own schema naming `Rating`, which ADR-0061 permits and `NOTION_PROPERTIES` still does not. The curation is pure in `src/domain/known-set.ts` and the wiring pages Notion; `config.ts`'s claim that "no code can name it" was corrected in place to the amended rule it has actually been under since ADR-0061.

The numbers are the deliverable and they are readable: 288 rows, 149 rated, **120 members across 33 weeks**, and the exclusions are 139 unrated, 14 `Nope`, 15 the agent wrote. Forty-eight per cent unrated is the risk the ticket named, and the response ADR-0063 prescribes is the one taken — publish the n rather than loosen the rule. Twelve of the 33 weeks fall in January–March, which is exactly the twelve ticket 05 needs and exactly where `fixtures/wikipedia.html` truncation hurts least, so that ticket's stated preference can be satisfied without trading anything for it. Five weeks hold more than five members, and the `Rotate`/`AOTY` secondary number is reported for those five alone, because below the cap no choice was forced.

One decision worth its ADR: the frozen set is a **gitignored** file and the record is a committed one. The set names the albums Ben likes and the ones he does not, this repository is public, and `AGENTS.md` says that is not committed — so `known-set.json` stays on his machine and `docs/evidence/known-set-freeze.md` carries the counts (ADR-0066). The `--out` flag the script briefly had was deleted for the same reason: the only thing it bought was writing taste data somewhere not gitignored.

Both reviews earned their keep and four findings were real. The paging used bare `fetch`, so a 429 part way through the database would have lost the whole read rather than being retried like every other provider call — it goes through `httpAdapter` now. `z.enum(RATINGS)` would have aborted the freeze if Ben ever adds a fifth option to his own column, which is the opposite of the tolerance the schema's comment promises; the name is read as a string and matched here. The dedup key was the MusicBrainz id where a row had one, so a release entered twice — once with an id, once without — would have counted twice and inflated the `k` the Back-test divides by; it keys on artist and title, which is what most of these rows have. And an unreadable `Release Date` would have thrown out of `toISOString` and killed the run, where it is now one more row reported as undated. Two smaller things: the `Rotate`/`AOTY` arithmetic was living untested in the script and is now `preferredCount` beside `curate`, and the record prints it only above the cap. 543 tests, `npm run check` green.

One thing I noticed while reading the frozen output and recorded rather than acted on: ten of the 120 members are EPs by their own titles, and an EP is eligible only at four tracks and twenty minutes. A week where the agent misses one of those may be the agent correctly refusing it — the superset problem this ticket is about, in format rather than in taste. It belongs to ticket 05's eligibility labels, not here. Next: ticket 05, harvesting the twelve weeks, which now has its twelve weeks to pick.

## 18 September 2026 (evening) — ticket 05: twelve weeks, recorded once

The outcome was the Golden Dataset's harvested half: twelve cases under `fixtures/eval/`, the `hits / min(k, 5)` back-test wired into the pass, and $0.2296 of live model time turned into 1,043 frozen MusicBrainz answers. Every one of the twelve **completed** — none reached the thirty-step ceiling that a fourteen-day window hit in milestone 2, which is the clearest evidence yet that ADR-0062 was right to make the windows weekly. The metric and the week-selection rule are pure and tested; the harvest is wiring, and `git diff src/agents/` is still empty.

Two things were learned by harvesting rather than by planning. The first is Ben's and it is a real defect: the week ending 2026-01-02 opens on 2025-12-27, and both Sources are *year* pages, so six of its seven days were never captured. The case was harvested, read, and swapped for 2026-04-03 — which incidentally gave the sample a second above-cap week at `k = 8`. The general case is carried-forward item 6: a real run between the last Friday of December and the first of January is quietly blind to most of its window, with no warning at all, because nothing was truncated. The second is what the replays measured: **eight of the nineteen releases labelled eligible across the four replayed weeks were carried by no Source page at all**. That is `unlisted` doing precisely the job ADR-0059 invented it for. Without the word, each would have counted as the agent failing to find a release that was never in front of it, and the fix would have been attempted in the wrong half of the system.

The reviews caught one bug that would have quietly poisoned every pass. `00-smoke`'s window ends on 2026-01-16, which is a real Known Set week with `k = 4`, and the back-test keyed on the resolved window alone — so a hand-built fixture serving one Source would have been scored against Ben's January albums in perpetuity, and ticket 06's mutants would have inherited the same fault from their parents' `now`. A case is back-tested only when its slug *is* its week now. Five smaller ones were real: a corrupt `known-set.json` read as an absent one, a non-200 MusicBrainz answer recorded as a 200 body, the frozen set re-parsed in the harvest with a cast that laundered `Rating` past its union, the identity split duplicated in two files, and every case pinned at `09:00+11:00` — an instant that resolves to the previous week anywhere west of UTC+2. All twelve are repinned to noon UTC, checked across five timezones.

What is not proven is the criterion as written. Four cases replayed end to end; the other eight are checked only for the *presence* of their recordings, by a test that parses every manifest and resolves every file it names. The model is the one thing a pass does not freeze, so a replay can ask a question no recording answers — which throws, is reported, and skips that case rather than ending the pass. The full proof is ticket 08's baseline, and buying it here would have been running ticket 08 early with the money spent twice. 564 tests, `npm run check` green. ## 21 September 2026 — ticket 06: the eight cases no real week supplied

The reviews were worth more than the build.
