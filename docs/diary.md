# Riff Radar Project Diary

Plain-language updates for people following the project, written at the end of a working session. Newest entries first. Keep these readable by anyone — no jargon, no code; the technical record lives in decisions.md and git history.

## 11 September 2026 — Setting up the ground rules for coding assistants

The goal today was housekeeping rather than building: give the coding assistants a clear, written answer to three questions they kept having to guess at. Where do tasks and specs live? What words do we use to mark a task as "ready" or "needs more detail"? And which documents should be read before touching anything? Those answers now live in a new `docs/agents/` folder, with a short summary in `AGENTS.md` pointing at them. Tasks will be kept as plain markdown files in the project rather than in an external tool, which suits a small solo project and keeps everything in one place.

Two things came out of it that were worth catching. The project brief had moved into the `docs` folder at some point, but several documents still pointed at its old location — those are fixed. And the assistants' default setup expects one file per decision in a `docs/adr/` folder, which contradicts our existing habit of keeping all decisions in a single `decisions.md`. We kept our habit and wrote the difference down, so nobody quietly starts a second decision log. Next: back to the actual product work, starting with the first milestone in the project brief.

## 11 September 2026 (later) — Pinning down what the first working version actually does

The goal was to define Milestone 1 and nothing else: no code, no later milestones. We worked through it as a long question-and-answer session, starting from how Ben actually finds new music on a Friday morning and working outward to what the software should do. That starting point turned out to matter, because the real habit differs from the original plan in ways worth knowing about. The plan assumed the system would search the web; in practice Ben reads four specific websites he trusts. The plan assumed it would look at albums that had just come out; one of those sites lists albums that haven't been released yet. Both differences are now settled in favour of the real habit, which means the project brief needs a small edit that hasn't been made yet.

The session produced three documents: a glossary of the project's own words, twelve recorded decisions with the reasoning behind each, and a specification of the first milestone covering the command, the sources, what counts as an eligible album, how taste is described, what the agent is allowed to do, when it stops, what gets recorded, and what stops it writing to Notion. Two useful things surfaced along the way. Ben's own mental model of taste is simpler than the one proposed — lock in the favourites, block the ones he won't listen to, and let everything in between be surfaced by looking at labels, band members and genre — so the design was simplified to match. And the existing Notion database is missing five fields the first version needs, so those have to be added by hand before anything can run. Next: agree the brief edits, add the Notion fields, then start on the loop itself.

## 11 September 2026 (later still) — Choosing the tools and deciding where to test

With the first milestone defined, this session settled two things that had been left open: what to build it with, and where the tests should attach. The language is TypeScript, chosen on the grounds that Ben already thinks in it — working in something less familiar would spend effort on the language rather than on the agent loop, which is the whole point. The thinking model will be DeepSeek V4.1 Flash, rented from a hosting company called Fireworks rather than run locally. Almost nothing extra is being installed: recent versions of Node can already run tests, talk to the internet and store data in a database file, so the project takes only three small libraries.

The more interesting decision was where to put the test boundary. Everything unpredictable or outside the program — the model, the internet, the clock — goes through a single doorway that tests can substitute. The database deliberately does not, because a fake database would make the save-and-resume tests prove nothing. A gap also surfaced: the chosen model does not guarantee its answers match the expected shape, and the spec never said what happens when the agent proposes something malformed. It now retries up to three times and then stops. Two loose ends remain: the model's exact name and price could not be read from the outside, so Ben needs to copy them from his Fireworks account. Next: run /to-spec to turn this into an implementable specification.

## 11 September 2026 (end of day) — Borrowing a shape from the team's framework

A short follow-up settled how the project's files will be arranged. Colleagues of Ben's use a framework called Flue for this kind of work, and the plan is to build this one by hand first and possibly move to the framework later. So rather than inventing a structure, the project copies Flue's arrangement wherever that makes sense and ignores it where it doesn't — Flue expects an agent to be reachable over the web, and this one is a command you type, so the entry point differs by design. The payoff is that the cost of moving later is now visible up front: the two files a framework would take over are clearly separated from the rules and the data-fetching code, which would carry across untouched. Pleasingly, the file that would be thrown away is exactly the one the whole exercise exists to teach.

One small deliberate difference was recorded so nobody later mistakes it for an oversight: the framework uses one data-checking library and this project uses a different one, simply because Ben already knows it. Also confirmed the model's real name and prices, which turned up something worth catching — repeated text is charged about thirty times less than new text, so the record now counts the two separately, otherwise the running-cost figures would have been badly wrong. Next: turn all of this into an implementable specification.

## 14 September 2026 — The first code: a run that starts, stops and leaves a record

The goal was the first half of the first ticket, and deliberately only that half: make a run exist, without building the thinking part yet. So there is now a command you can type, a place for the settings, a database that records what happened, and a run that starts up, works out exactly which dates it is covering, writes down what it did, and stops — reporting honestly that it found nothing, because nothing has been built yet that looks. It sounds like very little, and that is the point: every safety rail the thinking part will need is already in place and already tested, so when it arrives it drops into something that already stops properly. Sixty-nine tests cover it, and a run can be read back out of the database with an ordinary database query and no special tools, which was one of the things we promised ourselves.

The interesting question of the session was what "the last seven days" actually means. A run started on a Friday morning in Sydney is, as far as the rest of the world's clocks are concerned, still Thursday night, so a naive reading would have quietly looked at the wrong week. It now uses local dates, counts today as one of the seven, and — importantly — writes the two real dates into the record rather than the number seven, so that reading a run back in six months still tells you what it covered. Two things need Ben's eye. A fourth small piece of tooling had to be installed to make the type checking work at all; it only exists while writing code and disappears at runtime, but it is one more than the three we said we would use, so it is written down as a decision awaiting approval rather than slipped in. And the run does read the taste file, slightly ahead of the ticket that formally introduces it, because the record it writes has to say which version of Ben's taste produced it. Next: the second half of the ticket — the loop itself, the part the project exists to learn.

A follow-up pass the same day cut the code back hard: 175 lines gone, no behaviour lost that anyone would miss. Most of it was machinery written out of habit rather than need — a credentials object carefully assembled and then thrown away unread, a hand-written date formatter that the language already ships, a hand-written error formatter that the validation library already ships, a directory-walker Node does in one call, and several small wrappers with exactly one caller each. Four things did change in ways worth knowing: the record now stores the command exactly as typed rather than a tidied-up version of it (the two real dates beside it carry the detail anyway), the taste-file error report is now the validation library's own wording, the shorthand for running the tool directly was dropped in favour of the one documented way, and the check on the date window now happens only where the command line is read instead of in two places that could drift apart. Six tests went with the code they covered. Next is still the loop.

## 14 September 2026 (later) — The loop itself

The goal was the second half of the first ticket: the part the project exists to teach. The agent now thinks. Each step it is asked what to do next, it answers with one action, and the program checks that answer before acting on it — and only then does anything happen. The four things it can ask for are fetching one of the three configured sites, looking a record up in MusicBrainz, searching the web, and finishing with its shortlist. Three of those still return made-up data on purpose, because the point of this sitting was the loop and its safety rails rather than the music; the real versions drop into the same slots over the next few tickets and nothing else has to change.

What matters is what happens when the model gets it wrong, which it will. An answer that is prose instead of an action, an answer that names a tool that does not exist, an answer whose details are malformed or simply the wrong shape, an answer proposing two actions where one was asked for — each is refused, written into the record as refused, and handed back to the model so it can correct itself. Three of those in a row and the run stops. So does thirty steps, or a quarter of a dollar spent, or a shortlist that does not meet the rules, or the model provider failing outright. Nine possible endings, exactly one recorded, and every one of them now has a test that drives it through a stand-in model. The record keeps what the model proposed, whether it was allowed, what was actually done, how long it took and what it cost, split into the three kinds of token because the cheap kind is thirty times cheaper and lumping them together would have made every future cost figure wrong.

Three things need Ben's eye. A quiet week — the model finding nothing worth proposing — is recorded as "nothing found" rather than as a failure, which is written down as a decision. The spending ceiling per run is set at 25 cents, also written down. And one promise in the ticket is still outstanding: we cannot yet confirm whether the model provider tells us how much of each request it served from its cache, because there is no API key in this sandbox. The machinery for both answers is built and tested, and a single command settles it — until then a run that gets no cache figures labels its own cost as a ceiling rather than a measurement. A short follow-up once the key arrived settled both outstanding questions, and turned up a third nobody had asked. The provider does report how much of each request it served from its cache, so running costs are a real measurement rather than a ceiling — and the numbers vindicate the design: after the first step, roughly nine tokens in ten are the cheap kind, which is the whole reason the unchanging part of the request was put at the front. The surprise was that the model, asked to choose one action, cheerfully asked for all three websites at once. Refusing that is correct and was already built, but a run would have refused the model's first perfectly sensible move three times and given up before fetching anything. The fix is to ask the provider to allow only one action at a time, which it honours; the refusal stays behind it as the guard, because a request is not a guarantee.

With that, the whole thing ran for real: nine steps, three site fetches, five record lookups and a shortlist of five, in about thirty-six seconds for a fifth of a cent. Every step is in the database with what was asked for, whether it was allowed, what came back, how long it took and what it cost, readable with an ordinary SQL query. The music is still invented — that is what the next tickets fix — but the loop, the rails and the record are real. Next: ticket 02, which replaces the first fake with real pages.

## 14 September 2026 (later still) — The music is real now

The goal was ticket 02, and only that: make the first of the three fake tools real. The agent now actually reads the three websites Ben reads. It asks for one, the page comes back, the markup is stripped out by hand — no library, because the model only needs the text to be legible, not perfect — and the text is handed to a second, much simpler model call whose only job is to turn a page of listings into a list of releases. That list comes back as data the program can count, tidy and compare, which is the part that matters: the same album listed on two of the three sites is now recognised as one record carrying both addresses, and where two sites disagree about the release date, both dates are kept and the disagreement is written down rather than quietly settled by whichever page was read first.

The decision worth knowing about is that second model call. It would have been possible to just hand the page text to the agent and let it hold the releases in its head, and that would have been less code — but then there would be nothing to deduplicate, nothing to count, and no way to notice a site that has stopped producing results. So the extraction is its own small call, and everything after it is ordinary arithmetic that can be tested without a network. The cost of that call is charged to the step that made it, otherwise the spending ceiling would stop working at exactly the moment the tokens get big; and the page text is capped before it is sent, because a full release calendar costs more than a whole run is allowed to spend. The page itself is stored whole in the database, so a bad reading can be examined later without going back to the website — which may by then have changed.

Three things need Ben's eye. A site that refuses us, lists nothing, or comes back unreadable no longer stops the run: it is recorded as a warning and the agent carries on with the other two, on the grounds that losing one of three sources is a degraded week and not a failed one — written down as a decision. The second model call is likewise written down as a decision, since the ticket left it open. And the test fixtures are hand-written rather than recorded from the real pages, because this sandbox has no outbound network access; they reproduce each site's shape faithfully enough to test the stripper and the client, but only `npm run smoke:sources` — run by hand, with a key — can confirm the real pages still look like that. That is the first thing to run when a key and a network are both available. Next: ticket 03, web search.

A follow-up once the network was opened up replaced two of the three hand-written test pages with the real thing, and the real thing corrected us twice. The Loudwire calendar lists the coming months first and the weeks just gone at the very end, so the cap on how much of a page we send was cutting off exactly the releases a backward-looking run asks about; and a calendar covers a year, so one fetch would have handed the agent a thousand releases and paid to resend them at every step afterwards. Discovery is now asked for one week at a time and the cap is sized from a real page rather than guessed. Both fixes came from looking at a page we had previously only imagined, which is the argument for keeping the captures whole and untidied.

Live, the two readable sources between them found twenty-six albums released in the past week, for a little over a cent. The third — Album of the Year — turns out to refuse us at the door: it answers every request with a bot challenge, and getting past that would mean pretending to be a browser on a site that has explicitly said no, which is not something this project should do. Ben's call was to run on the two that work, so the third is no longer configured at all rather than configured and failing — a run has thirty steps and spending one knocking on a shut door buys nothing but a warning we already know the wording of. The page it served is kept as evidence, and its address sits in the decision record one line away from coming back if it ever opens up or someone finds a replacement. Worth knowing too that reading the Wikipedia page took a minute and a half of model time — discovery is the slow part of a run now, and the whole thing still costs less than two cents. Next: ticket 03, web search.

Ben ran the whole thing for real at the end of the day, and it worked: ten steps, two live websites, a shortlist of five albums actually released in the past week, for under two cents. Three of the five were found on both sites and correctly recognised as the same record rather than counted twice, which is the thing the dedup was written for and the first time it has been seen doing its job outside a test. The cost breakdown was the pleasing part — reading the two pages accounted for almost all of it, and every step after that was billed at the cheap rate, so the loop itself is nearly free and it is discovery that costs money. Worth writing down, because it means the lever for making runs cheaper is the pages, not the thinking.

One thing is important not to mistake for success. The albums, the dates and the web addresses are all real, but the identity check is still the stand-in from the last ticket, so every MusicBrainz identifier in that shortlist is made up and the agent's one-line justifications say "confirmed" about a confirmation that was fabricated for it. The agent is reporting honestly what it was told; the tool lied. That is exactly what the next ticket replaces, and nothing writes to Notion until two tickets after that, so no invented identifier can escape — but it is the sort of thing that looks finished and is not, so it is written down rather than admired. Next: ticket 03, web search.


## 14 September 2026 — ticket 03: the second fake becomes real

The goal was ticket 03 and only that: make `web_search` a real search. Brave's API was Ben's pick over scraping DuckDuckGo — which blocks anything that does not claim to be a browser, and this project does not claim that — and over Wikipedia's search, which is too thin for underground metal. It answers with JSON over a plain GET and takes its key in a header, so the only change the seam needed was an optional headers argument on `http`, added to what the project already sends rather than replacing it. A search that is refused, rate-limited, empty, or answers with something unparseable is a warning on the step and the run keeps going, exactly as a disappointing source already did.

The more interesting half was not the search. The rule that a release may only come from one of the configured sites has lived in the prompt since the beginning, which means it has been a request rather than a rule: nothing stopped the model shortlisting something it read in a search result, or simply remembered. The shortlist validator now takes the run's discovered releases and rejects any item that names something else, and since only a source fetch can add to that list, the route from a search to a Notion row no longer exists in the code. Proving it meant breaking seven existing tests whose shortlists were invented, which is the useful kind of test failure: they had been asserting on releases no source in the test had ever listed. What remains is Ben's: `npm run smoke:search` with a Brave key, to check that the body Brave really serves is the shape the client parses — the automated test uses the documented shape, not a capture, because capturing one needs the key. Next: ticket 04, MusicBrainz, the last fake.
